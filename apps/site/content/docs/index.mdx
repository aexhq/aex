# Aex documentation

A session is one long conversation with a model that can do things. It keeps
the whole history, runs on its own Linux machine, reads the files you mount for
it, calls tools, and can start helpers of its own. You send text and point the
model at files by path.

## Quickstart

### Create the account and first workspace key

The minimal onboarding path is the native CLI:

```sh
aex account create --name first-workspace-key --output json
```

This command needs no existing AEX credential. It opens Google sign-in in your
system browser, completes an S256 PKCE exchange through the fixed local
callback, provisions your personal account and its one fixed workspace if
needed, and mints a workspace key with all five workspace scopes. The browser
must be available on the same machine, and `127.0.0.1:53682` must be free for
the callback.

The output contains `accountId`, `accountState`, `email`, `userId`, `workspace`,
and `apiKey`. Store `apiKey.value` immediately in your secret manager: it is
returned once and cannot be recovered. Use it as `AEX_WORKSPACE_API_KEY` with
the SDK or `AEX_API_KEY` with the CLI. Do not save the whole command output in
source control; if the value is lost, mint a replacement.

`account create` closes its temporary dashboard session and never saves or
prints that session credential. When an automation environment already has a
dashboard session from the supported Google sign-in, expose it through
`AEX_DASHBOARD_SESSION` or store only a non-secret reference to it:

```sh
aex config set dashboard-session-ref env:AEX_DASHBOARD_SESSION
aex account bootstrap
aex api-key create --name automation
aex api-key list
aex api-key revoke "$API_KEY_ID"
```

`account bootstrap` prints the current personal account and fixed workspace.
`api-key create` prints only the new one-time key value in text mode; JSON and
NDJSON include its metadata. Omit `--scope` for all workspace scopes, or repeat
it to select from `sessions:read`, `sessions:write`, `sessions:delete`,
`resources:read`, and `resources:write`. Listing returns metadata only, and
revocation takes the key ID, never the secret value.

The launch surface deliberately has no organization or multi-workspace CRUD,
device authorization, account-token flow, or admin fabrication command. Fresh
account creation therefore requires the Google browser-and-PKCE ceremony; the
CLI does not bypass identity verification for unattended provisioning.

### Start a session

Install `@aexhq/sdk`, then provide one workspace API key and the provider key
that this session will encrypt and own.

```ts
import { Aex, newId } from "@aexhq/sdk";

const aex = new Aex({ apiKey: process.env.AEX_WORKSPACE_API_KEY! });
const session = await aex.sessions.sessionCreate({
  body: {
    provider: "openai",
    model: process.env.AEX_MODEL!,
    providerApiKey: process.env.AEX_PROVIDER_API_KEY!,
  },
  idempotencyKey: crypto.randomUUID(),
});

const committed = (async () => {
  for await (const frame of aex.sessions.sessionMessagesStream({
    sessionId: session.id,
  })) {
    if (frame.kind === "committed" && frame.message?.role === "assistant") {
      return frame.message;
    }
  }
  throw new Error("message stream ended before the assistant committed");
})();

await aex.sessions.sessionMessageSend({
  sessionId: session.id,
  body: { text: "Inspect the repository and report the failing tests." },
  idempotencyKey: crypto.randomUUID(),
});
console.log(await committed);

await aex.sessions.sessionTerminate({
  sessionId: session.id,
  body: {},
  operationId: newId("operation"),
});
```

Your provider key is accepted for that one session, encrypted before it is
stored, and never returned to you. You can use OpenAI, Anthropic, DeepSeek,
xAI, Meta, Moonshot AI, or Alibaba. Name the exact model you want, and check
that it supports the tools or structured output your session needs.

## Sessions

Creating a session starts the machine warming up in the background and returns
straight away, without waiting for it to be ready. You can watch that progress
in telemetry. The first tool call that needs the machine waits for it, and
wakes it if it has gone to sleep.

Every session gets a machine unless you turn it off. With
`sandbox.enabled: false` no machine is allocated, and tools that need one
return a clear error the model can handle instead of hanging. Remote MCP
servers still work without a machine; mounted files, MCP servers you run as a
process, and pinned packages all need one.

There are three ways to stop. Cancel ends the current message and leaves the
session idle. Terminate destroys the machine but keeps the transcript and
telemetry. Delete removes everything the session owns, and is safe to call
again if it is interrupted; files you uploaded to the workspace survive. A
session lasts up to eight hours and can start at most 12 helper agents, nested
no more than three deep.

## Files and mounts

A workspace file has one current value per name. Replace that value with text
or bytes, a link for Aex to fetch, or a direct upload. When a session is
created it looks up the names you asked for and pins their paths, so replacing
a file later cannot change a session that is already running.

```ts
await aex.workspaceFiles.put(
  "agent-guide",
  { type: "text", text: "Run the focused tests before changing source." },
  { mediaType: "text/markdown" },
);

const fileSession = await aex.sessions.sessionCreate({
  body: {
    provider: "openai",
    model: process.env.AEX_MODEL!,
    providerApiKey: process.env.AEX_PROVIDER_API_KEY!,
    registered: {
      mounts: [{ name: "agent-guide", path: "/workspace/AGENTS.md" }],
    },
  },
  idempotencyKey: crypto.randomUUID(),
});
```

Use `aex.workspaceFiles.upload(name, bytes)` for images, PDFs, video, archives,
and anything else. Messages themselves are text only: tell the model which file
or folder under `/workspace` to look at. Downloads are checked against the
exact size and SHA-256 digest Aex reports.

## Tools, MCP, and structured output

Out of the box the model can use `bash`, `read_file`, `edit_file`,
`write_file`, `mcp_call`, `storage_persist`, `create_subagent`,
`wait_subagents`, and `stop_subagent`. A large tool result leaves a short
preview in the transcript and keeps the full text in a file on the machine.
`storage_persist` is the wire name for `storage.persist`, which saves a file
from the machine back to your workspace.

You can attach MCP servers when you create the session, either over HTTP or as
a process on the machine. Their headers and environment values are encrypted
for that session and never returned. Strict JSON output works when the model
you chose supports it natively; Aex will not fake it with prompting and call it
strict.

```ts
const toolSession = await aex.sessions.sessionCreate({
  body: {
    provider: "openai",
    model: process.env.AEX_MODEL!,
    providerApiKey: process.env.AEX_PROVIDER_API_KEY!,
    mcpServers: [{
      name: "docs",
      transport: { kind: "remote_http", url: "https://mcp.example.com" },
    }],
  },
  idempotencyKey: crypto.randomUUID(),
});

await aex.sessions.sessionMessageSend({
  sessionId: toolSession.id,
  body: {
    text: "Inspect the docs tool and return the affected files.",
    responseFormat: {
      kind: "json_schema",
      schema: {
        type: "object",
        properties: { files: { type: "array", items: { type: "string" } } },
        required: ["files"],
        additionalProperties: false,
      },
    },
  },
  idempotencyKey: crypto.randomUUID(),
});
```

The transcript keeps text, tool calls, and tool results in the same shape
whichever provider you use. Independent tool calls can run at the same time,
but their results are recorded in the order the model asked for them.

## Streaming and telemetry

The message stream sends small NDJSON frames. Preview frames are a best effort
and never hold the model up. A `gap` frame tells you the stream fell behind or
lost something, `committed` is the durable truth, and `reconcile` replaces a
preview that turned out to be wrong.

The telemetry stream carries assistant output, tool activity, runtime events,
logs, spans, usage, gaps, and heartbeats. Once the live connection ends, Aex
keeps compressed copies you can replay or download. Token usage comes from a
separate trusted path and is never guessed from what the machine reported.

## Credentials and billing

Account, API key, and billing calls need a dashboard session from signing in
with Google. Session and file calls need a workspace API key. One `Aex` client
can hold both, and it only ever sends each one to the service it belongs to.

```ts
const account = new Aex({
  dashboardSession: process.env.AEX_DASHBOARD_SESSION!,
  apiKey: process.env.AEX_WORKSPACE_API_KEY!,
});

const [balance, cards, usage] = await Promise.all([
  account.billing.billingBalanceGet(),
  account.billing.billingPaymentMethodsList(),
  account.billing.billingUsageGet({ query: { category: "runtime", limit: "20" } }),
]);

const topUp = await account.billing.billingTopUpCheckoutCreate({
  body: { amountCents: "2000" },
  idempotencyKey: crypto.randomUUID(),
});
console.log(balance, cards, usage, topUp.url);
```

Adding a card and topping up happen on hosted pages. Aex only ever shows you
the display details of a saved card, your balance, a permanent record of every
transaction, and usage you can filter by session, provider, model, or kind of
work. Raw card details never reach the Aex API.
